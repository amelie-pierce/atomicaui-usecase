# Adding use cases

## Current rule: one use case = one business action (component > UI type > use case)

Rewritten 2026-11-20 (`fm/usecase-business-action-pilot`, Button, Dialog and AlertDialog only); it replaces the earlier "component > UI type > variant" rule. The current implementation has since migrated every gallery use case to the option model described below.

- A use case is one business action (Submit, Download CSV, Back to top, Reset inputs). The title names the action (`Download CSV button`); the look (the former variant, `Secondary solid`) is the `look` field of `usecase.ts`, shown in the Document and above the preview, never a tree level. Tree: component > UI type (Single button, Button group, Icon button) > use case. The same action with another look is not another use case: each case states its own `look`, the catalog derives the use case's `looks` from them, and the preview shows a Look select (first look = `example.tsx`, every other = `looks/<look-slug>.tsx`, `catalog/build-catalog.ts` `buildLooks`); the chosen look decides the example, the code, the Used-in apps and the In context cases (`withLook` in `catalog/app-views.ts`). Today Button-007 (Close info dialog button) and Button-032 (Open field help button) have two looks.
- Button keeps only what a button performs itself. A composite UI whose action is the whole modal (Reset confirm, Accept licence, Send feedback, Delete confirm, Save template, Welcome dialog) is one use case of Dialog or AlertDialog. AlertDialog has no card of its own: its `alert-dialog.meta.ts` sets `parent: 'Dialog'`, so its use cases (`AlertDialog-001`..`004`, ids unchanged) are the `Alert / Confirm` UI type of the Dialog page and tree entry, they sit under Dialog in the tree, and the old `#/AlertDialog` opens the Dialog page. Any component can be folded into another the same way with `parent`. App differences of the same action and look stay inside the use case as the app-group toggle; states or row kinds of the one action keep the radio group of case names.
- Open points for the next conversion: `AlertDialog-001` still documents the Reset action of HCS, ACE, ADM and ADC that `AlertDialog-003` now holds with HS and FD too (fold them when AlertDialog is converted); Button popover footers (`Button-021`, `Button-022`) stayed Button group use cases because the popover is not a modal.
- Migration of 2026-11-20: Button went from 31 variants to 42 use cases (ids `Button-001`..`042`; the first pass had 44, then the same-action pairs Close info dialog button and Open field help button were merged: old 44-id `Button-015` -> `Button-007` (FD group), `Button-038` -> `Button-032` (HS, ADM, PFD, AGPD groups), 016..037 -> one lower, 039..044 -> two lower), Button-018 left Button entirely (Reset confirm and Delete confirm -> `AlertDialog-003`, `-004`; Accept licence, Save template, Send feedback, Welcome dialog -> `Dialog-004`..`007`; old `Dialog-004`, `-005` -> `-008`, `-009`); the old Button-011 Centred action already existed as `AlertDialog-002`. The old-to-new table is in the PR description; old ids are retired and the URL hash keeps no alias.
- Decide types and looks by measuring computed styles in the running gallery; headless Chromium via Playwright when chrome-devtools-axi answers BRIDGE_NOT_READY. IconButton is no longer a component: its use cases are in Button's Icon button type.
